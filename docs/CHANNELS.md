# Управление каналами Gul

**Статус: архитектурный план, не реализовано.** Аудит исходников: 2026-10-08.
Этот документ не меняет действующий VPS, конфигурацию или права пользователей.
Текущий релиз с исправлениями выпускается отдельно от этой функции.

Первая версия имеет две роли: **владелец** управляет каналами, **участник**
подключается и общается. Пользовательские роли, модераторы и индивидуальный
доступ к закрытым каналам пока не входят в первый этап.

## Что есть сейчас

| Область      | Действующая реализация                                                                                                                    | Ограничение                                                                              |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Вход         | Общий пароль сервера, произвольный ник; `server/internal/broker/gul_http.go`, `login`                                                     | Нет постоянного пользователя или владельца                                               |
| Личность     | Новый случайный session ID и broker bearer на каждый вход; `server/internal/broker/gul.go`, `gulSession`                                  | Session ID и ник нельзя использовать как постоянного владельца                           |
| Каналы       | ID 0–3, имена и дерево заданы в `stateLocked`                                                                                             | Нет создания, переименования, удаления или сохранения каналов                            |
| API          | `/api/gul/login`, `/api/gul/state`, `/api/gul/channel`, `/api/gul/audio`, `/api/gul/screen`, `/api/gul/logout`; `gul_http.go`, `register` | `/api/gul/channel` переключает канал, а не управляет им                                  |
| Конфигурация | `server/internal/broker/public_config.go`, `PublicConfig`                                                                                 | Нет admin/owner поля, базы, списка каналов или reload; неизвестные JSON поля отклоняются |
| Медиа        | Комната `gul-channel-<id>`; `gul_grant.go`                                                                                                | `role=voice/screen` обозначает тип медиа, а не роль пользователя                         |
| Права JWT    | Разрешены публикация и подписка; voice также публикует DataChannel                                                                        | Нет индивидуальных ограничений голоса, демонстраций и чата                               |
| Клиент       | `desktop/src/main/validation.ts`, `channelId` и `tree`                                                                                    | ID ограничены 0–3, детей не более четырёх                                                |

Roster сейчас публикуется целиком для всех вошедших. Его сборка индексирует
фиксированный массив через `channelId - 1`: динамический каталог требует
замены этой логики, а не только увеличения допустимого ID.

Сессии хранятся в RAM, lease составляет 60 секунд, polling продлевает его.
Перезапуск broker требует нового входа. Серверные LiveKit API ключи клиентам
не выдаются; это ограничение сохраняется.

## Постоянная личность и владелец

Рекомендуемая небольшая модель без регистрации по почте:

- Сервер имеет постоянный случайный `serverId`, пользователь — `memberId`.
  Ник является только отображаемым именем: совпадение, изменение или
  повторный ввод ника не передают права.
- Вход участника подтверждается индивидуальным случайным credential не менее
  256 бит. Сервер хранит только его digest, привязанный к memberId и serverId.
  Это не человеческий пароль и не общий пароль REALITY.
- Владелец создаётся однократно локальной bootstrap-командой администратора
  сервера. Его роль хранится в базе. Первый вошедший, выбранный ник и знание
  общего пароля не делают человека владельцем.
- Владелец выдаёт одноразовое приглашение с ограниченным сроком действия.
  При принятии сервер создаёт участника и индивидуальный credential.
  Приглашение по умолчанию выдаёт только роль участника; его принятие и
  создание пользователя происходят одной транзакцией.
- Полученный credential остаётся в Electron main. Renderer получает только
  memberId, роль и разрешённые действия. Сохранение секрета требует явного
  согласия и защищённого safeStorage; Linux `basic_text` не используется.
  При недоступном keyring интерфейс честно сообщает, что вход не сохранён.
- Нужен предусмотренный способ восстановления через локальную команду
  владельца: повторная выдача credential и отзыв предыдущего. Потеря ответа
  принятия приглашения не должна превращать одноразовый invite в многоразовый.

Общий пароль и существующий профиль остаются транспортным доступом к
REALITY. Они не заменяют индивидуальную личность. Отзыв участника не требует
раздавать всем новый транспортный пароль: доступ проверяется в broker/SFU.

Единственного владельца нельзя удалить или понизить обычным API. Передача
владения и несколько владельцев — отдельная будущая функция. Owner credential
не является LiveKit admin key и не даёт клиенту прямой RoomService доступ.

## Хранение и версии

Для каталогов каналов, пользователей и приглашений рекомендуется небольшой
SQLite store с транзакциями и версионированными миграциями. Конкретный Go
driver выбирается и закрепляется при реализации; сейчас зависимость не добавлена.
Директория базы имеет права 0700, база и вспомогательные файлы — 0600.

Минимальные записи:

| Запись  | Поля                                                                        |
| ------- | --------------------------------------------------------------------------- |
| Server  | serverId, schemaVersion, catalogVersion, defaultChannelId                   |
| Member  | memberId, displayName, owner/member, credentialDigest, authVersion, revoked |
| Invite  | inviteDigest, expiresAt, consumedAt; issuer memberId                        |
| Channel | постоянный числовой ID, name, position, version, open/closing/deleted       |

Broker bearer и media JWT не записываются в эту базу. Логические сессии
остаются временными и ссылаются на постоянного участника.

Channel ID сохраняется при переименовании и не переиспользуется после удаления.
Это исключает присоединение старого grant к другому каналу с прежним ID.
Начальная миграция сохраняет существующие ID 0–3 и их имена; переход корневого
узла 0 в категорию не совмещается с первой реализацией CRUD.

`catalogVersion` и `channel.version` относятся к каталогу, а существующий
`session.revision` — к media поколению пользователя. Переименование,
перестановка и создание соседнего канала не переподключают голос или экран.
Запись подтверждается клиенту только после успешного commit.

## Первый этап: открытые каналы

Владелец видит кнопку добавления и меню переименования/удаления. Участник видит
обычный список каналов. Скрытие кнопок — удобство; каждое действие повторно
проверяет постоянную роль вызывающего на сервере.

Предлагаются фиксированные POST маршруты, сохраняющие узкий transport allowlist:

- `/api/gul/channels/create`: имя, позиция, ожидаемая catalogVersion.
- `/api/gul/channels/update`: ID, имя/позиция, ожидаемая channel.version.
- `/api/gul/channels/delete`: ID и ожидаемая channel.version.
- `/api/gul/invites/create`: выпуск приглашения участника владельцем.
- `/api/gul/invites/redeem`: одноразовое принятие до индивидуального входа.

Это предложения API, а не существующие endpoints. Индивидуальный вход и
отзыв credentials также требуют нового строгого контракта.

Первая версия создаёт только открытые каналы. Имена ограничены по длине,
контрольные символы запрещены, вывод экранируется React. Количество каналов и
размер response ограничиваются; точный лимит согласуется с размером сервера.
Не добавляются категории, произвольные роли, наследуемая матрица разрешений
или настройки отдельного получателя голоса.

Удалять разрешено только пустой канал. Служебный корневой узел 0 и обязательный
канал входа защищены от удаления.
«Пустой» означает отсутствие broker sessions, ожидающих входов и реальных
voice/screen участников SFU. При занятости возвращается 409, при недоступной
проверке SFU — ошибка без сообщения об успешном удалении.

Удаление сериализуется с join/grant/admission: сначала закрывается вход,
затем без удержания SQL-транзакции или глобального mutex проверяется SFU,
после повторной проверки версии фиксируется tombstone. Незавершённое closing
состояние восстанавливается определённо после перезапуска. Поздний join не
должен создать комнату удалённого канала. Перенос пользователей при удалении
занятого канала откладывается, чтобы первый CRUD не обрывал чужой разговор.

Ответ `/state` дополняется каталогом, его версией и capabilities вызывающего
участника. Изменение каталога подхватывается существующим polling. Запросы с
устаревшей version получают 409 и требуют обновления списка, а не молчаливого
перезаписывания чужого изменения. Можно добавить ограниченный operation ID
для повторной отправки после потерянного ответа создания.

## Admission: старый JWT не должен обходить сервер

Это обязательная серверная граница для закрытых каналов и строгого удаления.
Текущий `RemoveParticipant` отключает активного участника, но не отзывает
уже выданный JWT. Первичный token живёт 90 секунд, SFU может обновлять его.
Сокращение TTL и проверка `/channel` не устраняют повторный вход старым JWT.

Сейчас `deploy/livekit/prepare.py`, `proxy_config`, направляет `/rtc*` прямо
в SFU. Предлагается узкий broker admission proxy для всех разрешённых
`/rtc`, `/rtc/validate`, `/rtc/v1`, `/rtc/v1/validate`. SFU и RoomService
по-прежнему доступны только через внутреннюю сеть.

До каждого join/reconnect/validation proxy проверяет:

1. Подпись, issuer, срок, media роль и точный room подписанного JWT.
2. Живую broker session, memberId/authVersion и текущий channel revision.
3. Случайную session nonce, подписанную в attributes: 31-битный session ID
   может когда-нибудь повториться и один не защищает от старого token.
4. Наличие канала, отсутствие closing/deleted и актуальное право входа.

Nonce сохраняется SFU при token refresh — это необходимо подтвердить на
закреплённом LiveKit v1.13.8 и проверить реальным reconnect. Если SFU не
сохраняет обязательные claims, требуется иной доказанный способ admission;
молчаливого пропуска проверки быть не должно.

Проверка касается реального внешнего пути к SFU, а не только loopback bridge
официального клиента. JWT, его query и credentials не попадают в access logs.
При отзыве/смене сессии закрываются принадлежащие ей signaling соединения,
удаляются оба SFU участника и запрещается новый admission. Уже действующий
WebRTC поток также требует подтверждённого SFU cleanup: закрытие WebSocket
само по себе не считается мгновенным прекращением media.

Готовность этого пути нужна до обещания, что удалённая комната недоступна
со старым JWT. CRUD только метаданных в доверенных открытых комнатах можно
прототипировать раньше локально, но он не является завершённой этой гарантией.

## Позже: список допущенных участников

После общего CRUD и admission добавляется whitelist по **memberId**, не нику.
Политика первого закрытого канала может иметь только `open` или
`allowedMemberIds`; владелец управляет ей. Не допущенный участник не получает
roster, grants или room access этого канала.

Одна проверка входа распространяется сразу на голос, просмотр/публикацию экрана
и чат: `sendChat` сейчас отправляет reliable LiveKit DataChannel `gul.chat.v1`
из voice Room, а не отдельный broker message. Все новые и обновлённые grants
считаются по актуальной политике, включая screen companion.

Отзыв доступа к занятому каналу требует отдельного lifecycle: новая policy
атомарно запрещает admission/grants, cleanup отключает voice и screen,
клиент закрывает capture, picker, playback и историю текущего канала. Ошибка
SFU cleanup остаётся явным pending/retry состоянием, без обещания, что media
уже прекратилось. После внешнего await сервер повторно проверяет session и
policy version перед выдачей любого нового grant.

Принудительный переход клиента также требует нового контракта: текущий
`brokerState` отвергает неожиданные selfChannel/revision. Нельзя просто заменить
эти поля в roster. Нужны валидированное событие/session update и новая media
epoch либо явное прекращение сессии с повторным разрешённым входом.

Раздельные запреты «можно слушать, нельзя говорить/демонстрировать/писать»
откладываются. При их реализации `canPublishSources` и `canPublishData` должны
соответствовать серверной политике. Пользователь без права публикации экрана
может оставаться зрителем: endpoint screen не должен без причины запрещать
subscribe-only companion. Local mute не является серверным запретом речи.

TDD начинает каждый этап. Критические сценарии:

- Участник с ником владельца, дубликат имени и изменённый renderer не получают
  owner права. Неверный credential, повторный/просроченный invite отклоняются.
- Каналы, memberId и owner сохраняются после полного server/client restart;
  ошибки записи не подтверждаются как успех. Нет plaintext/basic_text fallback.

  revoke/delete. Проверяется реальный SFU/REALITY путь, а не только mock.
- Для будущего whitelist не допущенный member не получает чужой roster, voice,
  screen или chat; поздний callback старой epoch не изменяет новую сессию.
- Обычные голос, VAD/PTT, экран со звуком и смена канала продолжают проходить
  существующие E2E; coverage новых модулей не менее 80% строк/ветвей/функций.

## Внедрение без изменений живого VPS сейчас

Сначала store/auth/CRUD/admission проверяются на отдельном локальном Docker
stand с собственными credentials и двумя Electron клиентами. После этого
готовятся совместимые client/server версии, миграция начальных каналов и
проверка восстановления. Старый клиент ограничен ID 0–3: динамический каталог
требует явного version/capability handshake и понятного отказа «обновите клиент»,
а не случайной ошибки валидации посреди разговора.

Только отдельное согласованное переключение после завершения живой сессии
может установить новый broker/proxy и приватную базу на VPS. Сейчас ничего не
перезапускается. Graceful HAProxy reload не делает перезапуск broker незаметным:
его RAM сессии теряются, поэтому бесшовный переход не обещается.

Существующий REALITY профиль и транспорт сохраняются. Закрытые ACL включаются
только после полного admission/revocation E2E; до этого все каналы открытые.
