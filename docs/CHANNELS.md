# Управление каналами Gul

Реализовано и проверено локально и на действующем VPS 8 октября 2026 года.
Режим включается явно через `statePath` и bootstrap владельца; на нашем VPS
он включён в alpha.6. Без него остаются общий пароль и каналы 0–3.

## Владелец и участники

Только владелец создаёт, переименовывает, удаляет каналы и меняет доступ.
Закрытый канал доступен выбранным постоянным участникам и владельцу.
Остальные видят его название и замок, но не список находящихся внутри.
Ник — отображаемое имя: его совпадение или изменение не передают права.

Общий пароль остаётся доступом к транспорту и открытым каналам. Гость может
в них общаться; для закрытого канала нужен личный ключ участника.
Ключ содержит 256 случайных бит и привязан к постоянным `serverId`/`memberId`.
Сервер хранит digest. Первый вход или знание общего пароля не назначают владельца.

Владельца однократно создаёт администратор локальной командой:

```sh
gul-livekit-server -bootstrap-owner -config /private/path/broker.json \
  -owner-output /private/path/owner-key.json
```

Команда отказывается заменять существующий каталог или экспорт. Конфиг и
экспорт имеют режим 0600, родительские каталоги — 0700. Экспорт импортируют
кнопкой личного доступа в Gul и хранят отдельно от Git. Формат:
`gul-member-key-v1`, поля `serverId`, `memberId`, `credential`.

Владелец выдаёт одноразовое приглашение с ограниченным сроком. Electron main
генерирует личный ключ до принятия; сервер атомарно сохраняет digest и
расходует приглашение. После потери ответа можно повторить с тем же ключом
на том же сервере. Повтор с другим ключом запрещён.

Постоянный ключ и broker bearer не выдаются renderer. Импорт использует
нативный выбор файла, ограниченный regular-file read и строгую проверку JSON.
Сохранение требует отдельного согласия и защищённого OS safeStorage;
Linux `basic_text` запрещён. При недоступном хранилище импортированный ключ
можно использовать в текущем процессе; UI сообщает, что он не сохранён.
Недоступный сохранённый ключ не приводит к молчаливому входу гостем.
Постоянная запись подтверждается только после проверки личности сервером.

## Каталог

Хранилище — ограниченный атомарный JSON: временный файл 0600, fsync, rename,
fsync каталога и эксклюзивный file lock. Максимум 64 канала, 128 участников,
64 записи в списке допуска; файл не более 512 КиБ. Сессии и JWT не сохраняются.
Для небольшой компании SQLite и дополнительные runtime зависимости не нужны.

Если fsync после rename даёт неопределённый результат, хранилище становится
нездоровым. Broker отзывает сессии, закрывает signaling и запрещает grants и
admission до нового открытия каталога. Старый ACL в памяти не продолжает
разрешать вход вопреки записанному файлу.

ID 0 и 1 защищены от удаления и закрытого доступа; канал 1 служит каналом
входа. Остальные удаляются только пустыми: проверяются broker сессии,
ожидающие signaling входы и реальные voice/screen участники SFU.
Занятость даёт 409; недоступная проверка не означает успешное удаление.
Удалённый ID никогда не переиспользуется.

Создание проверяет `catalogVersion`, изменение и удаление — версию канала.
Конфликт требует обновить список. CRUD метаданных не меняет media epoch
и не переподключает голос или экран. Категории, перестановка, модераторы,
несколько владельцев, передача владения, отзыв постоянного ключа и отдельная
CLI-команда его восстановления пока не реализованы.

## API и совместимость

Права повторно проверяются сервером. IPC и transport allowlist разрешают
только фиксированные маршруты:

| Маршрут | Назначение |
| --- | --- |
| `GET /api/gul/info` | Версия протокола, serverId и возможности |
| `POST /api/gul/login` | Общий пароль и необязательный личный ключ |
| `GET /api/gul/members` | Постоянные участники, только владельцу |
| `POST /api/gul/channels/create` | Имя, политика и версия каталога |
| `POST /api/gul/channels/update` | ID, версия, имя и политика |
| `POST /api/gul/channels/delete` | ID и версия пустого канала |
| `POST /api/gul/channels/permissions` | Список допуска, только владельцу |
| `POST /api/gul/invites/create` | Одноразовое приглашение |
| `POST /api/gul/invites/redeem` | Принятие с новым личным ключом |

Managed server требует `protocolVersion: 2`; старый клиент получает 426.
Новый клиент поддерживает старый broker: только 404 на `/info` разрешает
legacy fallback. Ошибка, смена `serverId` или некорректный ключ его не разрешают.

## Admission и отзыв доступа

В managed режиме HAProxy направляет `/rtc`, `/rtc/validate`, `/rtc/v1` и
`/rtc/v1/validate` через broker admission. Остальные HTTP пути тоже идут
в broker, чтобы default SFU backend не обходил проверку. TURN остаётся
отдельной TLS веткой, RoomService — внутренним API.

Проверяются подпись, issuer, expiration, media роль, точные room/identity,
serverId/memberId/authVersion, живая сессия, случайная nonce, revision и ACL.
Сохранение этих attributes при refresh подтверждено на LiveKit v1.13.8.

Отзыв сначала запрещает grants и admission, затем закрывает signaling,
ждёт завершения ожидающих входов и удаляет оба SFU участника.
Неудачный cleanup явно возвращает `media_cleanup_pending` и повторяется
maintenance циклом. Отозванный участник отключается; новый вход возвращает
его в открытый канал. Старый и обновлённый JWT не обходят закрытый доступ.

## Проверки

- Go unit/race: роли, совпадающие ники, invites, CAS, bounds, restart,
  private storage, pending upgrade с игнорированием отмены, ошибки записи.
- TypeScript unit: wire/IPC границы, protected storage, server binding,
  epoch fences и отсутствие скрытого перехода в гостя.
- Electron UI: owner CRUD, whitelist, invite, отсутствие управления
  у участника и сохранение media lifecycle при CRUD.
- Настоящие REALITY и LiveKit: join/refresh, занятый delete, rename без
  закрытия signaling, revoke voice/screen с нулевым SFU roster, старые
  обновлённые JWT, сохранение после restart и отсутствие reuse ID.

Создайте отдельный `stand_reality.py --managed` и задайте
`GUL_MANAGED_STAND_DIR` для `managed-channels.live.spec.ts`.
Физические Windows 10 ↔ Ubuntu и длительная игровая сессия остаются
отдельными проверками готовности к beta.
