# Критический разбор PLAN.md

## Резюме

План внутренне логичен и хорошо структурирован по милстоунам, но опирается на несколько фактически неверных посылок о ключевых зависимостях, и именно они ломают M2–M3. Три главные: (1) gumble вообще не использует UDP — весь голос идёт в UDPTunnel поверх TLS/TCP, а схема §1 обещает «UDP voice»; (2) duplex в miniaudio на WASAPI/CoreAudio/PulseAudio — это не общий hardware clock, а наивный software-ring между двумя асинхронными устройствами с дропом кадров и добивкой тишиной, то есть базовое условие сходимости speex AEC из §4.2 не выполняется ни на одной целевой ОС; (3) speexdsp работает только с int16, а RNNoise ждёт float в int16-диапазоне, так что описанный float-пайплайн §4.3 не собирается как написан. Дополнительно: API gumble для TX/RX (небуферизованные каналы, синхронный encode+TLS write внутри общего readRoutine, отсутствие sequence number, незакрываемые стримы) прямо противоречит инварианту «ноль аллокаций и блокировок», а gopus на arm64 требует системный libopus, что рушит обещание «ноль зависимостей у пользователя» на Apple Silicon. Вне аудио не проработаны: модель доверия TLS (только insecure-флаг вместо TOFU), подпись/нотаризация бинарей для M4, Wayland для глобального PTT и тестируемость аудио в CI.

## Находки

### [CRITICAL] gumble не передаёт голос по UDP — весь звук идёт в UDPTunnel поверх TLS/TCP

Схема §1 заявляет «TCP/TLS control + UDP voice». Это неверно. В `Conn.WriteAudio` (conn.go:65-98) пакет пишется как `c.writeHeader(1, ...)` + `c.Conn.Write(...)`, где тип 1 = UDPTunnel, а `c.Conn` — это `tls.Conn` поверх TCP из `DialWithDialer` (client.go: `tls.DialWithDialer(dialer, "tcp", addr, tlsConfig)`). Приём идёт через `handleUDPTunnel` (handlers.go:79). `handleCryptSetup` (handlers.go:898) возвращает `errUnimplementedHandler` — OCB-крипто для UDP не реализовано вовсе. UDP в gumble используется только в `ping.go` для server-browser пинга. Последствия для проекта: head-of-line blocking при потере пакета (весь поток встаёт до ретрансмита), всплески задержки в разы, зависимость джиттер-буфера от TCP-таймингов, невозможность честно обещать «низкую задержку голоса». Это меняет требования к джиттер-буферу: нужен не anti-jitter на 60 мс, а буфер, переживающий TCP-берсты в сотни миллисекунд.

Источники: <https://github.com/layeh/gumble/blob/master/gumble/conn.go> · <https://github.com/layeh/gumble/blob/master/gumble/handlers.go> · <https://github.com/layeh/gumble/blob/master/gumble/client.go> · <https://github.com/layeh/gumble/blob/master/gumble/ping.go>

### [CRITICAL] Duplex в miniaudio — не общий clock; посылка §4.2 неверна для всех трёх целевых ОС

§4.2 объявляет: «Открываем одно full-duplex устройство malgo (capture+playback в одном callback / с общим clock). Это обязательное условие корректной работы speex AEC». Исходник miniaudio опровергает это. На асинхронных бэкендах (WASAPI, CoreAudio, PulseAudio, AAudio — все вызывают `ma_device_handle_backend_data_callback`, miniaudio.h:31765/31815, 35111/35230, 41566/41571, 39346) duplex реализован через `ma_duplex_rb` — промежуточный ring между двумя независимыми потоками устройств. Комментарий в miniaudio.h:6092-6100 дословно: «The idea of the duplex ring buffer is to act as the intermediary buffer when running two asynchronous devices in a duplex set up… At the moment this is just a simple naive implementation, but in the future I want to implement some dynamic resampling to seamlessly handle desyncs». При рассинхроне: на переполнении `Overrun. Not enough room in the ring buffer for input frame. Excess frames are dropped.` (miniaudio.h:20594), на недоборе `If there's not enough data in there for the whole frameCount frames we just use silence instead for the input data` (miniaudio.h:20636). То есть дрейф часов лечится дропом/вставкой сэмплов в микрофонный тракт — ровно то, что разрушает сходимость адаптивного фильтра speex AEC и делает его расхождение невидимым для нашего кода. Единый поток «прочитал capture → callback → записал playback» есть только на синхронных бэкендах (ALSA/sndio/OSS, miniaudio.h:20343-20352), которых нет на macOS и Windows. Дополнительно: `config.playback.pDeviceID` и `config.capture.pDeviceID` в duplex задаются раздельно (miniaudio.h:198-199), так что «одно устройство» — это соглашение нашего кода, а не свойство API; типовой пользователь с USB-микрофоном и встроенными динамиками физически не может выполнить требование §4.2, а запрет раздельных устройств в v1 убивает UX.

Источники: <https://github.com/mackron/miniaudio/blob/master/miniaudio.h> · <https://pkg.go.dev/github.com/gen2brain/malgo>

### [CRITICAL] speexdsp — только int16; RNNoise — float в int16-диапазоне. Float-пайплайн §4.3 не собирается как описан

§4.3 рисует `mic f32[480] → speex_echo_cancellation(...) → speex_preprocess_run(...) → rnnoise_process_frame(...) → f32 → int16`, то есть одну конверсию в самом конце. Фактически: весь API speexdsp принимает `spx_int16_t` — `speex_echo_cancellation(SpeexEchoState*, const spx_int16_t *rec, const spx_int16_t *play, spx_int16_t *out)` и `speex_preprocess_run(SpeexPreprocessState*, spx_int16_t *x)`. RNNoise принимает float (`float rnnoise_process_frame(DenoiseState*, float *out, const float *in)`), но в масштабе int16, а не ±1.0: в `examples/rnnoise_demo.c` вход читается как `short tmp[480]` и передаётся как `x[i] = tmp[i]` без нормализации. Это критично, потому что в `denoise.c:358` детектор тишины — абсолютный порог `if (!TRAINING && E < 0.04) { … return 1; }`, а при `silence` функция не вызывает `compute_rnn` и возвращает `vad_prob = 0` (denoise.c:468-493). Подача нормализованных ±1.0 float даст: шумодав не работает вообще и VAD всегда 0 — то есть при VAD-режиме микрофон никогда не откроется, и отладка этого займёт дни. Реальный тракт требует минимум трёх конверсий (f32→i16 перед AEC, i16→f32 перед RNNoise, f32→i16 перед gumble), что нужно зафиксировать в спецификации, иначе «инвариант» §4.3 будет нарушаться молча.

Источники: <https://github.com/xiph/speexdsp/blob/master/include/speex/speex_echo.h> · <https://github.com/xiph/speexdsp/blob/master/include/speex/speex_preprocess.h> · <https://github.com/xiph/rnnoise/blob/master/examples/rnnoise_demo.c> · <https://github.com/xiph/rnnoise/blob/master/src/denoise.c> · <https://github.com/xiph/rnnoise/blob/master/include/rnnoise.h>

### [CRITICAL] Client.AudioOutgoing() блокирует и аллоцирует — прямое нарушение инварианта §4.5

`func (c *Client) AudioOutgoing() chan<- AudioBuffer` создаёт **небуферизованный** канал `ch := make(chan AudioBuffer)` (client.go:178-193). Внутренняя горутина делает `previous := <-ch; for p := range ch { previous.writeAudio(c, seq, false); previous = p; … }`. Три следствия, которых нет в плане: (1) отправка в канал блокируется до тех пор, пока горутина не выполнит синхронно `encoder.Encode()` (cgo-вызов в libopus) и `client.Conn.WriteAudio` под `c.Lock()` с записью в TLS-сокет — при заторе TCP это блокировка на неограниченное время, и любая горутина, пишущая туда напрямую из аудио-тракта, встанет; (2) схема с `previous` намеренно придерживает один кадр, чтобы уметь пометить последний как `final` — это скрытые постоянные +10 мс к исходящей задержке; (3) `AudioBuffer` ([]int16) потребляется асинхронно чужой горутиной, поэтому преаллоцированный буфер переиспользовать нельзя — аллокация на каждый кадр (100/с) обязательна, что противоречит «ноль аллокаций». Плюс ошибка `writeAudio` игнорируется (`previous.writeAudio(c, seq, false)` без проверки) — сбой отправки голоса не диагностируем.

Источники: <https://github.com/layeh/gumble/blob/master/gumble/client.go> · <https://github.com/layeh/gumble/blob/master/gumble/audio.go> · <https://pkg.go.dev/layeh.com/gumble/gumble#Client.AudioOutgoing>

### [CRITICAL] Входящие аудиостримы gumble: небуферизованный канал на общем readRoutine + утечка горутин

В `handleUDPTunnel` (handlers.go:159-175) для каждого пользователя создаётся `ch := make(chan *AudioPacket)` — небуферизованный — и далее `ch <- &event` выполняется **внутри единственного `readRoutine`**, который обрабатывает все протокольные сообщения. Значит любой затор нашего RX-потребителя (GC-пауза, блокировка на мьютексе миксера, медленный jitter push) останавливает обработку чата, дерева каналов и Ping → срабатывает `Conn.Timeout` (20 с по умолчанию, conn.go:33) и/или серверный timeout → разрыв соединения. Плана на это нет. Второе: канал **никогда не закрывается** и `item.streams[user]` никогда не удаляется — в коде стоят TODO `// TODO: decoder pool` и `// TODO: de-reference after stream is done` (handlers.go:105-106). При этом godoc обещает «It is the implementer's responsibility to continuously process AudioStreamEvent.C until it is closed». Контракт невыполним: наши per-user горутины никогда не завершатся сами, а при выходе/входе пользователя gumble пересоздаст `*User` и заведёт новый канал и новую горутину — утечка за длинную сессию.

Источники: <https://github.com/layeh/gumble/blob/master/gumble/handlers.go> · <https://github.com/layeh/gumble/blob/master/gumble/audiolisteners.go> · <https://pkg.go.dev/layeh.com/gumble/gumble#AudioListener>

### [MAJOR] gumble выбрасывает sequence number — джиттер-буфер и PLC построить не на чем

В `handleUDPTunnel` номер последовательности читается и немедленно отбрасывается: `// TODO: use in jitter buffer` / `_, n = varint.Decode(buffer)` (handlers.go:115-121). Структура `AudioPacket` содержит только `Client, Sender, Target, AudioBuffer, HasPosition, X, Y, Z` — ни seq, ни timestamp. Последствия: §4.4 «per-user jitter buffer» может лишь сглаживать темп поступления, но не умеет детектировать пропуски, определять начало/конец talk-spurt и делать packet loss concealment; M5 «адаптивный джиттер-буфер (или speex_jitter)» требует seq на входе — speex_jitter_buffer_put принимает пакет с timestamp, которого у нас не будет. Обходные пути (форк gumble или свой handler поверх сырых UDPTunnel-байт) нужно решить до M2, потому что они меняют границу слоя internal/mumble.

Источники: <https://github.com/layeh/gumble/blob/master/gumble/handlers.go> · <https://pkg.go.dev/layeh.com/gumble/gumble#AudioPacket>

### [MAJOR] gopus требует системный libopus на arm64 — ломает «ноль зависимостей» на Apple Silicon и в CI

layeh.com/gumble/opus — обёртка над layeh.com/gopus. В gopus вендоренные исходники opus-1.1.2 подключаются файлом с ограничением `// +build amd64,cgo 386,cgo` (opus_nonshared.go), а для всех прочих архитектур действует `// +build !amd64,!386,cgo` с директивой `// #cgo !nopkgconfig pkg-config: opus` (opus_shared.go). README gopus подтверждает: «opus development library (only on platforms where the shared library is used)». Практически это значит: на Apple Silicon (рабочая машина — darwin/arm64) и на раннере macos-latest в GitHub Actions (тоже arm64) обязателен `brew install opus pkg-config`, а собранный бинарь динамически слинкуется с `/opt/homebrew/lib/libopus.0.dylib` и не запустится ни на одном чужом Mac без Homebrew. То же на Windows-on-ARM и arm64-Linux. Это прямо противоречит §0 («ничего не требует установки зависимостей у пользователя») и §9 («внешних dev-пакетов не требовать»). Отдельно: вендоренный opus 1.1.2 — релиз 2015 года, без современных arm64-оптимизаций и без улучшений PLC из 1.5.x.

Источники: <https://github.com/layeh/gopus/blob/master/opus_shared.go> · <https://github.com/layeh/gopus/blob/master/opus_nonshared.go> · <https://github.com/layeh/gopus/blob/master/README.md> · <https://pkg.go.dev/layeh.com/gumble/opus>

### [MAJOR] Битрейт Opus не задан; дефолт gumble даёт жёсткий потолок 32 кбит/с

`AudioDefaultDataBytes = 40` (audio.go) — 40 байт на кадр 10 мс = 32 кбит/с. `AudioBuffer.writeAudio` вызывает `encoder.Encode(a, len(a), dataBytes)`, где dataBytes = `client.Config.AudioDataBytes`, то есть это hard cap на размер payload. При этом gumble/opus в `NewEncoder` хардкодит `e.SetBitrate(gopus.BitrateMaximum)` и не предоставляет API для смены битрейта — единственный рычаг качества у нас это `AudioDataBytes`. Комбинация «целевой битрейт = максимум, но payload обрезан до 40 байт» — не тот режим, в котором Opus звучит лучше всего; для «звук как у больших» нужен явный целевой битрейт (ориентир 48–64 кбит/с для моно-речи). Сервер здесь не ограничитель: дефолт mumble-server.ini — `bandwidth=558000`. План нигде не фиксирует целевой битрейт и не описывает реакцию на `ServerSync.MaxBandwidth` (gumble лишь прокидывает его в `ConnectEvent.MaximumBitrate`, handlers.go:270, но сам ничего не подстраивает).

Источники: <https://github.com/layeh/gumble/blob/master/gumble/audio.go> · <https://github.com/layeh/gumble/blob/master/opus/opus.go> · <https://github.com/mumble-voip/mumble/blob/master/auxiliary_files/mumble-server.ini>

### [MAJOR] RX-кадры не 480 сэмплов: официальный клиент Mumble по умолчанию шлёт 20 мс

§1 и §4.4 неявно предполагают, что входящий PCM приходит кадрами нашей сетки. Это не так: дефолт «Audio per packet» в официальном клиенте Mumble — 20 мс, gumble декодирует до `AudioMaximumFrameSize = 48000/1000*60` = 2880 сэмплов и возвращает `output[:ret*channels]` фактической длины. Значит per-user jitter/mixer должен корректно принимать 480/960/1920/2880 сэмплов и переупаковывать в кадры 480. Это не ресемплинг (частота одна), но требует явного слоя реассемблирования, которого в §4.4 нет — а он влияет на размер и логику джиттер-буфера. Практический сценарий, который вылезет сразу: отладка через официальный клиент Mumble рядом с нашим.

Источники: <https://www.mumble.info/documentation/user/audio-settings/> · <https://github.com/layeh/gumble/blob/master/gumble/handlers.go> · <https://github.com/layeh/gopus/blob/master/opus_shared.go>

### [MAJOR] Выравнивание AEC reference отложено в M5, но является условием приёмки M3 — внутреннее противоречие

DoD M3: «разговор на колонках без наушников не даёт слышимого эха собеседнику». При этом «Автоопределение задержки AEC ref (корреляция) вместо ручной константы» стоит в M5, а §4.4 ограничивается фразой «кладёт его копию в AEC reference ring». Ручная константа не спасёт: фактическая задержка = период playback-буфера miniaudio + внутренний `ma_data_converter` на playback-стороне (кадры, которые мы пишем, ещё ресемплируются до частоты устройства ПОСЛЕ нашего tap-а, miniaudio.h:20623+) + буфер драйвера/ОС + акустический путь. Она разная на CoreAudio/WASAPI/PulseAudio, меняется при смене устройства и при переключении Bluetooth-профиля. В спецификации нет sample-clock accounting: не сказано, что ref должен адресоваться по счётчику воспроизведённых сэмплов со сдвигом на известную output latency, и не выбрано между `speex_echo_cancellation` (мы сами выравниваем) и парой `speex_echo_playback`/`speex_echo_capture` (внутренний буфер speex, документирован как «delayed by two frames»). Также `AECTailMs = 120` — нижняя граница: speex_echo.h рекомендует filter_length «should generally correspond to 100-500 ms», а для колонок в комнате 120 мс мало.

Источники: <https://github.com/xiph/speexdsp/blob/master/include/speex/speex_echo.h> · <https://github.com/mackron/miniaudio/blob/master/miniaudio.h>

### [MAJOR] malgo сам берёт глобальный mutex в каждом аудио-callback — инвариант «ноль блокировок» нарушен библиотекой

`//export goDataCallback` в malgo/device.go:194-217 начинается с `deviceMutex.Lock(); callback := dataCallbacks[pDevice]; deviceMutex.Unlock()`, где `deviceMutex` — пакетная глобальная `sync.Mutex`, разделяемая с `Device.Uninit()` (который под ней же удаляет записи из map). То есть на каждый период аудио происходит захват глобального мьютекса ещё до того, как выполнится наш код, а `Uninit` из другой горутины конкурирует за него с живым аудио-потоком. Плюс это настоящий C→Go cgo-callback: он подчиняется планировщику Go и может быть задержан STW-паузой GC. План §4.5 объявляет «ноль аллокаций и ноль блокировок в audio callback» как неприкосновенный инвариант, но не рассматривает ни GC, ни этот факт. Отдельный источник мусора: gopus.Decode делает `output := make([]int16, d.channels*frameSize)` с frameSize = `AudioMaximumFrameSize` = 2880, то есть 5760 байт аллокации на каждый входящий пакет независимо от его реальной длины — при 5 говорящих это порядка 1.5 МБ/с мусора, подпитывающего те самые GC-паузы.

Источники: <https://github.com/gen2brain/malgo/blob/master/device.go> · <https://github.com/layeh/gopus/blob/master/opus_shared.go>

### [MAJOR] Порядок AEC → AGC → RNNoise объявлен «неприкосновенным инвариантом» без обоснования и, вероятно, неоптимален

§4.3 и §10.3 фиксируют порядок AEC → AGC (speex_preprocess) → RNNoise → gate. Проблема в том, что AGC выставлен до шумоподавления: в паузах речи AGC поднимает усиление, шум растёт, RNNoise получает более сложный (и нестационарный по уровню) вход, а нестационарное усиление ухудшает работу обученной сети. Общепринятая цепочка — AEC → denoise → AGC. Дополнительно `SPEEX_PREPROCESS_SET_ECHO_STATE` (подавление остаточного эха) требует, чтобы preprocess видел тот же сигнал, что вышел из AEC, — это выполняется, но привязка обязана быть сделана явно, а в чекбоксе M3 она упомянута одним словом «residual echo attach» без спецификации. Объявлять порядок инвариантом до первых измерений преждевременно: план сам себе запрещает менять его без отдельного обсуждения, хотя это ровно тот параметр, который тюнится по результатам golden-тестов.

Источники: <https://github.com/xiph/speexdsp/blob/master/include/speex/speex_preprocess.h>

### [MAJOR] Нет модели доверия TLS: только insecure-флаг, тогда как Mumble использует TOFU по отпечатку

§5 предусматривает лишь `insecure_tls=true` «в dev» и чекбокс «доверять сертификату» в UI. §8 говорит: «Локально клиент ходит с insecure_tls=true», а §7/M4 требует поднять прод-сервер на VPS по тем же материалам. Практически это означает, что для собственного VPS с self-signed сертификатом пользователи будут постоянно работать с полностью отключённой проверкой TLS — то есть без защиты от MITM, при том что по этому же соединению идёт и голос (UDPTunnel), и пароль сервера. Штатная модель Mumble — trust-on-first-use с сохранением отпечатка сертификата сервера и предупреждением при его смене. В плане её нет, и это не отмечено ни как риск, ни как задача. Смежно: клиентский сертификат (§5) — это фактически учётные данные пользователя; не сказано ни про права доступа к файлу ключа (0600), ни про то, что его потеря = потеря идентичности на сервере, ни про экспорт/импорт.

Источники: <https://www.mumble.info/documentation/user/certificates/> · <https://github.com/layeh/gumble/blob/master/gumble/client.go>
