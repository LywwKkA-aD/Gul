# Шумоподавление и VAD: RNNoise против DeepFilterNet, ONNX-моделей и FastEnhancer

## Вердикт: ОСТАВИТЬ С ИЗМЕНЕНИЯМИ

Оставляем RNNoise как шумодав и как VAD для первого релиза — это единственный кандидат, который одновременно нативно 48 кГц, имеет кадр ровно 480 сэмплов, представляет собой чистый C без сторонних зависимостей и тулчейнов, весит ~1.3 МБ в бинарнике, лицензирован BSD-3-Clause и бесплатно отдаёт vad_prob. Изменения к плану: (1) фиксируем коммит ветки main, а не тег v0.2, и вендорим сгенерированный rnnoise_data.c или weights blob в репозиторий; (2) прячем шумодав за интерфейсом Denoiser с сигнатурой на 480-сэмпловый кадр, чтобы DeepFilterNet (df_process_frame имеет ровно такой же контракт) можно было подставить без переписывания пайплайна; (3) DeepFilterNet в первый релиз не берём из-за замороженного апстрима, Rust-тулчейна в сборке и +40 мс задержки — держим как запасной вариант по качеству. ONNX-ветку (GTCRN, Silero VAD, sherpa-onnx) отклоняем целиком: 16 кГц плюс 11–80 МБ рантайма на платформу. FastEnhancer + faster-enhancer.c ставим на явный пересмотр через 3–6 месяцев — это лучший апгрейд-путь, но сейчас слишком сырой.

## Резюме

Текущий план (RNNoise как шумодав + его же vad_prob) в 2026 году остаётся правильным по существу, но требует двух уточнений. Первое: брать надо именно ветку main, а не тег v0.2 — модель в main обновлялась 2024-08 (skip connections) и 2025-01-30 (augmentation/loss tuning), и это уже ~1.34 M параметров против ~0.06 M у «того самого RNNoise 2018», по которому его до сих пор ругают в статьях; веса надо вендорить в репозиторий, а не тянуть 58.6 МБ с media.xiph.org на билде. Второе: главный кандидат на замену, DeepFilterNet, фактически заморожен — последний коммит 2024-09-25, последний релиз v0.5.6 (2023-08), а плановые CI-прогоны Rust CI и Python CI падают по состоянию на 2026-08-20; при этом он тянет Rust + cargo-c в сборку на трёх ОС, десятки МБ в бинарник и +40 мс алгоритмической задержки. ONNX-варианты (GTCRN, Silero через onnxruntime, sherpa-onnx) отпадают дважды: они работают на 16 кГц (ломает нашу 48 кГц-сетку) и требуют пер-платформенный рантайм на 11–80 МБ, что противоречит цели «один самодостаточный бинарник». Настоящая новость 2026 года — FastEnhancer (ICASSP 2026, MIT, живой, есть 48 кГц-конфиги) и его чистый C-рантайм faster-enhancer.c: 162 KiB библиотека, 565 КБ весов, 0.458 мс на кадр на M2 — но репозиторию три дня от роду, под первый релиз это ставить нельзя. NS внутри webrtc-audio-processing v2.1 — классический стационарный оценщик, отдельный DNN-шумодав он не заменяет, но если брать APM ради AEC3, он попутно закрывает проблему отсутствующего AGC в speexdsp FIXED_POINT.

GitHub API по Rikorose/DeepFilterNet: pushed_at = 2024-10-17, последний коммит в main — 2024-09-25 ("channel"), последний релиз v0.5.6 от 2023-08-31. Практический вывод: взяв DFN, мы берём на себя роль мейнтейнера снапшота с зависимостями 2024 года (tract 0.21, ndarray 0.15, rust-ini 0.21, MSRV 1.70).

### [MAJOR] Цена DeepFilterNet: Rust-тулчейн в сборке, десятки МБ бинарника, +40 мс задержки

Три конкретных издержки. (1) Сборка: cargo cinstall -p deep_filter требует nightly Rust плюс cargo-c на всех трёх ОС; для Windows и ARM в CI ещё и --features=vendored-openssl. Это ломает модель «Go + cgo + вендоренный C», ради которой выбирались speexdsp и RNNoise. (2) Размер: артефакты релиза v0.5.6 — libdeep_filter_ladspa .so для x86_64 Linux 52.7 МБ, aarch64 48.7 МБ, DLL для Windows 50.7 МБ; CLI deep-filter 26.9–39.2 МБ. Голая capi-статика будет меньше, но tract-onnx + rustfft + вшитая модель дают порядок «десятки МБ», а сама модель DeepFilterNet3 — 7.99 МБ в zip (чекпойнт model_120.ckpt.best — 11.9 МБ). (3) Задержка: config.ini даёт conv_lookahead = 2 и df_lookahead = 2 при hop 10 мс, то есть ~40 мс алгоритмической задержки против ~20 мс у RNNoise. Есть фича default-model-ll (низколатентная модель), но именно она в ONNX-виде весит 36.4 МБ. RTF по статьям: 0.19 на однопоточном ноутбучном CPU для DF1 и 0.04 на Core-i5 для DF2, то есть 0.4–1.9 мс на 10-мс кадр — в бюджет проходит, но это в 3–10 раз дороже RNNoise.

Источники: <https://github.com/Rikorose/DeepFilterNet/releases/tag/v0.5.6> · <https://arxiv.org/abs/2205.05474> · <https://arxiv.org/abs/2305.08227> · <https://github.com/Rikorose/DeepFilterNet/blob/main/libDF/Cargo.toml>

### [MAJOR] RNNoise в main — это не «RNNoise 2018»: модель выросла примерно в 20 раз, и обвинения в слабом качестве к ней уже не относятся

История файла model_version показывает, что веса переобучались после релиза v0.2 (2024-04-15): «New models with updated augmentation» (2024-08-12), «Add skip connections» (2024-08-19), «Augmentation/loss tuning, adding more noise data» (2025-01-30). Архитектура из torch/rnnoise/rnnoise.py: Conv1d(65->128, k=3) + Conv1d(128->256, k=3) + три GRU(256,256) + Linear(1024->32) для гейнов + Linear(1024->1) для VAD; суммарно 1 341 729 параметров, то есть примерно 1.34 M и порядка 134 MMAC/s при кадре 10 мс. Для сравнения, в таблицах статьи GTCRN строка «RNNoise (2018)» — это 0.06 M параметров и 0.04 GMAC/s с PESQ 2.29 на VCTK-DEMAND. Это разные модели, отличающиеся более чем на порядок по ёмкости. Публичных PESQ/DNSMOS для текущей модели main никто не публиковал, поэтому единственный честный способ решить — слепое A/B на своих записях, а не перенос цифр из статей.

Источники: <https://github.com/xiph/rnnoise/commits/main/model_version> · <https://github.com/xiph/rnnoise/blob/main/torch/rnnoise/rnnoise.py> · <https://github.com/Xiaobin-Rong/gtcrn> · <https://github.com/xiph/rnnoise/releases/tag/v0.2>

### [MAJOR] GTCRN отпадает по двум независимым причинам: 16 кГц и onnxruntime

GTCRN действительно хорош по эффективности — 48.2 K параметров, 33.0 MMAC/s, MIT, живой репозиторий (pushed_at 2026-08-03, LADSPA-плагин добавлен 2026-01-18), RTF 0.07 на i5-12400, и в таблицах он честно обыгрывает RNNoise-2018: VCTK-DEMAND PESQ 2.87 против 2.29, DNS3 DNSMOS OVRL 2.70 против 2.53, при этом сопоставим с DeepFilterNet (2.81). Но обучен и работает он на 16 кГц (VCTK-DEMAND и DNS3 — 16 кГц), а значит в нашем пайплайне потребует 48->16->48 ресемплинг и убьёт всю полосу выше 8 кГц. Для проекта, у которого явная цель «чистый звук на колонках», отрезать fullband ради шумодава — плохой размен. Второе: запускать его в Go придётся через onnxruntime либо через sherpa-onnx (Apache-2.0, Go API для GTCRN добавлено в PR #1991), а пакеты sherpa-onnx-go-* содержат преднасобранные бинарники — репозиторий sherpa-onnx-go-linux весит 445 МБ.

Источники: <https://github.com/Xiaobin-Rong/gtcrn> · <https://github.com/k2-fsa/sherpa-onnx> · <https://github.com/k2-fsa/sherpa-onnx-go-linux> · <https://github.com/k2-fsa/sherpa-onnx/releases/tag/speech-enhancement-models>

### [MAJOR] onnxruntime как таковой несовместим с целью «один самодостаточный бинарник»

Размеры официальных артефактов onnxruntime v1.29.0 (2026-08-12): linux-x64 11.1 МБ tgz, linux-aarch64 10.0 МБ, osx-arm64 41.6 МБ, win-x64 79.6 МБ zip, win-arm64 81.7 МБ. Это архивы; распакованные разделяемые библиотеки надо либо класть рядом с бинарником, либо линковать статически. Go-обвязки идут двумя путями и оба неудобны: yalue/onnxruntime_go грузит .so/.dll/.dylib динамически в рантайме, а покрытие Windows у большинства обвязок хромает, потому что onnxruntime на Windows рассчитан на MSVC, тогда как cgo требует MinGW. Минимальная сборка ORT технически уменьшает размер, но это отдельный большой CMake/C++ билд, который придётся вести самим на трёх платформах. Для одного шумодава и одного VAD эта цена не окупается.

Источники: <https://github.com/microsoft/onnxruntime/releases> · <https://onnxruntime.ai/docs/build/custom.html> · <https://pkg.go.dev/github.com/yalue/onnxruntime_go>

### [MAJOR] Настоящая новинка 2026 года — FastEnhancer, и у него уже есть чистый C-рантайм на 48 кГц

FastEnhancer (aask1357/fastenhancer, MIT, ICASSP 2026, репозиторий создан 2025-09-04, коммиты по 2026-07-03) — прямой ответ на архитектурную переусложнённость GTCRN/LiSenNet/FSPEN: простой encoder-decoder с RNNFormer-блоками. Вариант Tiny — 22 K параметров, 55 M MAC, RTF 0.012 на Xeon и 0.013 на M1, то есть в 3–5 раз быстрее GTCRN при сопоставимом качестве. Базовая конфигурация 16 кГц с hop 160 (10 мс) и алгоритмической задержкой в один кадр, но релизы ckpt-v1.0.0-48khz и onnx-48khz-v1 (февраль 2026) дают 48 кГц: n_fft 1024, hop 512 для T/B/S, 320 для M, 200 для L; в июле 2026 добавлен чекпойнт с дереверберацией. Отдельно и самое интересное для нас: kdrkdrkdr/faster-enhancer.c (MIT) — int8 C/SIMD-рантайм FastEnhancer-Medium на 48 кГц вообще без инференс-фреймворка, libfe.a 162 KiB, веса 565 108 байт, API из четырёх функций (fe_init/fe_run/fe_reset/fe_free), fe_run принимает ровно 320 сэмплов на вход и отдаёт 320, RTF 0.069 и 0.458 мс на кадр на Apple M2, PESQ 3.054 против 3.060 у fp32 ONNX-референса. Это буквально идеальная форма для cgo. Оговорка: репозиторий создан 2026-07-27, все коммиты уложились в трое суток, 21 звезда, один автор — под первый релиз брать нельзя. Плюс hop 320 не совпадает с нашими 480, но НОК равен 960, то есть два наших кадра ложатся ровно в три модельных, ценой не более 6.67 мс дополнительной буферизации.

Источники: <https://github.com/aask1357/fastenhancer> · <https://arxiv.org/abs/2509.21867> · <https://github.com/kdrkdrkdr/faster-enhancer.c>

### [MAJOR] NS внутри webrtc-audio-processing v2 не заменяет DNN-шумодав, но закрывает дыру со speexdsp AGC

Актуальные теги проекта по GitLab API: v2.0 от 2025-01-08 и v2.1 от 2025-01-22 (до этого v1.3 в сентябре 2023), код подтянут с апстрима WebRTC уровня M131. Пайплайн APM фиксирован: high-pass filter -> AEC3 -> NS -> AGC2. Его NS — классический оценщик стационарного шума, который вычитает оценку, набранную в паузах; на нестационарном шуме (лай, клавиатура, хлопок двери, babble) он заметно слабее обучаемых моделей, которые вместо этого удерживают речь. Для цели «чистый звук с первого релиза, разговор на колонках» его одного не хватит, и выкидывать отдельный шумодав нельзя. Но если APM всё равно берётся ради AEC3, то его NS + AGC2 закрывают ровно ту проблему, что зафиксирована в текущем плане: отсутствие AGC в speexdsp при FIXED_POINT-сборке. То есть APM v2.1 вытесняет speexdsp целиком, а RNNoise остаётся тяжёлой ступенью после него.

Источники: <https://gitlab.freedesktop.org/pulseaudio/webrtc-audio-processing/-/tags> · <https://gitlab.freedesktop.org/pulseaudio/webrtc-audio-processing/-/releases/v2.0> · <https://docs.pipewire.org/page_module_echo_cancel.html>

TEN VAD (TEN-framework/ten-vad, 2245 звезды, pushed_at 2026-02-02) действительно быстрее и точнее Silero: заявлено снижение RTF примерно на 32%, меньший размер библиотеки и заметно более быстрая реакция на переход речь->тишина, тогда как у Silero задержка в сотни миллисекунд. ### [MAJOR] Порядок ступеней в пайплайне важнее выбора шумодава

Любой из рассмотренных денойзеров — нелинейная спектральная обработка. Если поставить его до AEC, линейный фильтр AEC перестаёт сходиться, потому что связь между reference-сигналом и микрофоном перестаёт быть линейной. Правильный порядок: capture -> HPF -> AEC (AEC3) -> NS (RNNoise) -> AGC -> кодек. Reference для AEC берётся до всякой обработки захвата и никогда не должен содержать выход денойзера. Отдельно стоит помнить, что известная проблема с наивным ring-буфером miniaudio в duplex-режиме на CoreAudio/PulseAudio без компенсации дрейфа часов бьёт именно по AEC, а не по шумодаву, то есть выбор RNNoise против DeepFilterNet на неё никак не влияет и решать её надо отдельно. Наконец, RNNoise даёт vad_prob уже после подавления шума, что для гейта передачи скорее плюс: решение принимается по очищенному сигналу.

Источники: <https://docs.pipewire.org/page_module_echo_cancel.html> · <https://github.com/xiph/rnnoise/blob/main/src/denoise.c>

### [minor] 58 МБ весов RNNoise — проблема билда, а не размера бинарника

Проверено HEAD-запросом: rnnoise_data-0a8755f8...tar.gz отдаёт Content-Length 58 603 099 байт, и media.xiph.org отдаёт его очень медленно (за ~9 минут скачалось около 17 МБ, загрузка не завершилась). При этом в бинарник попадает не тарбол, а квантованные int8-веса: при 1.34 M параметров это порядка 1.3 МБ. autogen.sh дёргает download_model.sh с wget на каждой чистой сборке — для CI на трёх ОС это лишняя внешняя зависимость и точка отказа. README документирует два обходных пути: сгенерировать weights_blob.bin через dump_weights_blob и грузить через rnnoise_model_from_file, либо собирать с -DUSE_WEIGHTS_FILE и вообще не вшивать дефолтную модель. Есть также «little» модель — того же размера блоба, но более разреженная и потому быстрее.

### [info] Технически DeepFilterNet ложится на нашу сетку идеально — это делает его хорошим запасным вариантом

Из models/DeepFilterNet3.zip -> config.ini секция [df]: sr = 48000, fft_size = 960, hop_size = 480. То есть кадр ровно 10 мс = 480 сэмплов, один в один с нашей сеткой, без ресемплинга и без буферов-переходников. C API реально существует и кроссплатформенный: libDF/Cargo.toml объявляет crate-type = ["cdylib", "rlib", "staticlib"], фичу capi = [tract, default-model, ndarray, logging], метаданные capi для cargo-c, заголовок генерируется cbindgen (cbindgen.toml, language = C, cpp_compat = true). CI-матрица build_capi.yml покрывает linux x86_64/armv7/aarch64, macOS x86_64/aarch64, windows-msvc. Сама сигнатура — прямой аналог RNNoise: df_create(path, atten_lim), df_get_frame_length(), df_process_frame(st, in, out) -> local SNR, df_set_atten_lim, df_set_post_filter_beta, df_free. Инференс идёт через tract (чистый Rust ONNX-движок), то есть onnxruntime не нужен. Лицензия MIT OR Apache-2.0 (LICENSE-MIT + LICENSE-APACHE в libDF/).

### [info] RNNoise точно соответствует нашей аудиосетке, но есть две ловушки интеграции

src/denoise.h: FRAME_SIZE 480, WINDOW_SIZE 960, NB_BANDS 32, NB_FEATURES 65 — ровно наш кадр 10 мс на 48 кГц. Ловушка первая: rnnoise_process_frame ожидает float в шкале int16, а не в [-1, 1] — в examples/rnnoise_demo.c делается прямое x[i] = tmp[i] из short без нормализации. Если подать [-1, 1], шумодав будет считать сигнал тишиной. Ловушка вторая: в denoise.c есть буферы delayed_X/delayed_P/delayed_Ex — гейн, посчитанный на кадре N, применяется к спектру кадра N-1 (коммит «Adding one extra frame of delay», 2024-04-12), и демо явно выбрасывает первый выходной кадр через if (!first). Итого алгоритмическая задержка ~20 мс: 10 мс от перекрытия окна плюс 10 мс от отложенного кадра. API для VAD и загрузки моделей: rnnoise_process_frame возвращает vad_prob, есть rnnoise_model_from_buffer / from_file / from_filename, так что веса можно линковать как байтовый массив в Go и не таскать внешний файл. Лицензия BSD-3-Clause — MIT-совместима.
