## Вердикт: ОСТАВИТЬ С ИЗМЕНЕНИЯМИ

ОБОЛОЧКА — keep. Остаёмся на Wails v3; альтернативы честно проиграли: Tauri v2 и Electron ломают архитектуру «Go-ядро в одном процессе с UI», webview/webview_go фактически заброшен (последний push 31.08.2024), fyne/gio живы и активны, но это нативный UI — выбрасывать HTML-прототип, объявленный в CLAUDE.md источником визуальной правды, нерационально. Изменения только процедурные: пин точной беты в go.mod и CI без @latest, апгрейд отдельным PR по changelog, заранее записанный триггер отката на Wails v2.14.0. Отдельный плюс v3 именно для Gul — штатный app.GlobalShortcut закрывает пункт плана про PTT-хоткей без golang.design/x/hotkey. ФРОНТЕНД — keep-with-changes. React 19 + Tailwind v4 + zustand v5 подтверждены как актуальные, менять не на что; zustand особенно уместен, так как Wails-события приходят извне React и setState из колбэка не требует провайдера. ## Резюме

Оболочку заменять не надо, но план стоит ужесточить процедурно. Wails v3 — единственный вариант, сохраняющий Go+cgo-ядро в одном процессе с UI и дающий генерируемые типизированные биндинги; Tauri v2 зрелее, но превращает наш аудиодвижок в sidecar-процесс и добавляет Rust-тулчейн ради выгод, которых проект не потребляет. Главный риск v3 — не «беты ломаются» (внутри beta.0…beta.11 ломающих изменений публичного API нет), а то, что beta.N — это автоматические nightly с master (beta.0 от 02.08.2026, beta.11 от 20.08.2026) и публичной даты 3.0 нет; лечится жёстким пином и запретом @latest. Аргумент «взять Electron ради браузерного echoCancellation» разбивается конкретным фактом: Chromium подавляет эхо только от того звука, который проигрывает сам Chromium (electron#47043), поэтому весь плейбек пришлось бы унести в renderer и убить принцип «весь звук в Go». Зато оттуда следует полезный вывод для DSP-агента: тот же AEC3 доступен как отдельная C++-библиотека без Electron. По фронтенду стек актуален (React 19.2.8, Tailwind 4.3.3, zustand 5.0.15), но надо явно зафиксировать Vite 8 (Rolldown) и НЕ брать TypeScript 7 — до 7.1 на нём не работает typescript-eslint.

## Находки

### [MAJOR] Electron не даёт «бесплатный AEC»: Chromium гасит только собственный звук

Ключевой факт из расследования electron/electron#47043 (issue закрыт, статус confirmed): echoCancellation работал в Chrome и не работал в Electron ровно потому, что Chromium вычитает из микрофона только тот сигнал, который проигрывает сам Chromium, а не системный микс. Автор проверил это, включив музыку в Media Player при захвате через Chrome — она НЕ подавлялась; майнтейнер nikwen подтвердил обратный тест (музыка из Chrome подавляется, из Firefox — нет). Практический вывод для Gul: чтобы задействовать AEC3, весь плейбек удалённых голосов обязан идти через renderer (Web Audio), а захват — через getUserMedia. Это два IPC-перехода на кадр 10 мс (Go декодирует Opus -> IPC -> Web Audio -> getUserMedia -> IPC -> Go кодирует Opus) поверх собственной буферизации AudioWorklet, и это прямо отменяет правило PLAN.md «весь звук и протокол — в Go». Плюс Chromium+Node в поставке — порядок 100+ МБ на платформу против одного Go-бинаря, то есть отмена цели «один самодостаточный бинарник». Плюс позиция майнтейнеров (комментарий codebytere): патчить Chromium под такие баги они не будут, надо идти в upstream. Отдельно отмечу честности ради: ограничение «только свой звук» само по себе НЕ является регрессом относительно speexdsp — у нашего AEC референсом тоже служит только собственный плейбек; проигрыш именно в цене интеграции и размере, а не в охвате подавления.

Источники: <https://github.com/electron/electron/issues/47043> · <https://issues.chromium.org/issues/40815657> · <https://github.com/electron/electron>

### [MAJOR] Полезный побочный вывод: AEC3 доступен как C++-библиотека без Electron

Раз качество AEC3 — единственная реальная приманка Electron, её можно забрать напрямую. Модуль AudioProcessing из WebRTC (AEC3 + AGC2 + noise suppression + VAD + high-pass) сопровождается проектом PulseAudio как самостоятельная библиотека webrtc-audio-processing (сборка meson/ninja, лицензия BSD-3, то есть MIT-совместима; уже пакетируется дистрибутивами и FreeBSD как webrtc-audio-processing2). Это закрывает сразу три известные проблемы текущего DSP-плана: слабый MDF-эхоподавитель speexdsp, отсутствующий AGC в FIXED_POINT-сборке speexdsp и — что важнее всего — отсутствие компенсации дрейфа часов, поскольку у APM есть встроенная оценка задержки. Цена: C++ вместо чистого C (нужен cgo с CXX), заметно больший объём вендоринга и выше CPU на кадр 10 мс, чем у speexdsp. Это не зона решения моего компонента (оболочка), передаю как вход для DSP-агента — но именно этот путь, а не Electron, является ответом на вопрос «есть ли что-то новее speexdsp AEC».

Источники: <https://freedesktop.org/software/pulseaudio/webrtc-audio-processing/> · <https://www.freshports.org/audio/webrtc-audio-processing2/> · <https://gitlab.freedesktop.org/pulseaudio/webrtc-audio-processing>

### [MAJOR] TypeScript 7 брать нельзя: нет программного API до 7.1, typescript-eslint не работает

npm dist-tag latest у пакета typescript сейчас 7.0.2 — то есть наивное npm i -D typescript в 2026 притащит именно 7.x. Между тем официальный анонс прямо говорит: TypeScript 7.0 does not yet expose a stable programmatic API. Инструменты, которым нужны ts.createProgram/ts.factory — в первую очередь typescript-eslint — на 7.0 не запускаются; стабильный API ожидается в 7.1 (ориентир осень 2026, цикл 3-4 месяца). Microsoft выпустила совместимостный пакет @typescript/typescript6 (версия 6.0.2, Apache-2.0) с бинарём tsc6 для side-by-side установки. Хорошая новость для нас: в списке несовместимых названы Vue, Svelte, Astro, MDX и Angular (через Volar) — React/TSX там НЕТ, потому что трансформ JSX в Vite 8 делает oxc, а не TS. То есть выбор React вместо Svelte/Vue сам по себе снижает риск. Но type-aware линт в task lint (PLAN.md §9) на TS 7 сегодня не поднимется. Рекомендуемый апстримом путь миграции — сначала TypeScript 6.0, который вводит новые дефолты, а 7.0 их наследует: any TypeScript code that compiles cleanly with TypeScript 6.0 should compile identically in TypeScript 7.0.

Источники: <https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/> · <https://registry.npmjs.org/typescript/latest> · <https://registry.npmjs.org/@typescript/typescript6/latest> · <https://www.infoq.com/news/2026/08/typescript-7-released/>

### [MAJOR] Tauri v2: технически возможен с Go-sidecar, но выгоды для Gul отрицательные

Честная оценка, как просили. Механизм существует и документирован: externalBin в tauri.conf.json бандлит произвольный бинарь, разрешения выдаются на execute/spawn, связь — stdio, локальный сокет или встроенный HTTP. Трафик UI<->ядро у голосового клиента мизерный (события «кто говорит», уровни, mute — десятки сообщений в секунду), так что пропускная способность НЕ является препятствием; аудио в любом случае целиком остаётся в Go. Против — четыре пункта. (1) Появляется второй тулчейн: Rust и cargo в CI поверх уже имеющихся Go+cgo+Node, и Rust-glue надо писать и сопровождать. (2) Два процесса вместо одного: нужен супервизор и корректное убийство sidecar при падении UI, иначе осиротевший процесс продолжает держать аудиоустройство — для голосового клиента это заметный класс багов. (3) Теряются генерируемые типизированные Go->TS биндинги Wails, взамен ручной JSON-контракт; это именно то, что PLAN.md §1 закрепляет как способ связи UI и ядра. (4) Лицензия Tauri — Apache-2.0 против MIT у Wails; для MIT-проекта совместимо, но менее однородно. Плюсы Tauri (stable-статус, независимый аудит, тонкая capability-модель безопасности) реальны, но адресуют угрозы, которых у приложения для 6-15 друзей поверх собственного murmur нет.

Источники: <https://v2.tauri.app/develop/sidecar/> · <https://github.com/tauri-apps/tauri/discussions/3521> · <https://github.com/tauri-apps/tauri>

### [MAJOR] Реальный профиль риска Wails v3 beta: nightly-нумерация и отсутствие даты 3.0

Важное уточнение к формулировке «Wails v3 beta.11». Каждая бета помечена в теле релиза как automated nightly release generated from the latest changes on master, и темп это подтверждает: beta.0 — 02.08.2026, beta.11 — 20.08.2026, то есть 12 бет за 18 дней. Номер беты растёт от суточного цикла CI, а не от циклов стабилизации, поэтому beta.11 не значит «одиннадцатая выверенная итерация». Официальная страница статуса — Roadmap, помеченная как living document, без даты и без списка блокеров 3.0; формулировка компат-обещания мягкая: Beta APIs aim for stability, but prerelease defects and explicitly announced changes may still be corrected before v3.0.0. При этом releases/latest указывает на v2.14.0 (10.08.2026), то есть v2 продолжает получать релизы и остаётся рабочим планом отката. Дополнительный урок из beta.8: пайплайн бинарных релизов CLI удалён, установка только через go install — если бы онбординг-скрипт качал бинарь из GitHub Releases, он бы сломался. Практика: пинить точный тег и никогда не ставить @latest (что, к сожалению, советует официальная страница установки).

### [minor] Расхождение по иконкам: PLAN.md называет lucide-react, прототип нарисован на Phosphor

В PLAN.md §2 в строке Frontend зафиксировано «Иконки — lucide-react», но в Gul-Prototype-offline.html используются классы веб-шрифта Phosphor (встречаются Phosphor, Phosphor-Fill, phosphor-logo:before). Обе библиотеки живы и лицензионно чисты: @phosphor-icons/react — 2.1.10, MIT, peerDependencies react >= 16.8, то есть с React 19 совместим; lucide-react — 1.33.0, ISC. ### [minor] Тулчейн упаковки подтверждён, но «самодостаточный бинарник» на Linux условен

Подтверждаю заявленное в задаче: wails3 покрывает NSIS и MSIX на Windows, .app/.dmg/universal с нотаризацией на macOS, AppImage/deb/rpm/AUR на Linux — это реальные задачи Taskfile в build_assets, а не обещания в документации. Отдельно замечу про сборку нашего cgo-ядра: darwin-таск ставит CGO_ENABLED=1 и MACOSX_DEPLOYMENT_TARGET=12.0 по умолчанию, то есть speexdsp/RNNoise/miniaudio соберутся штатно, и есть build:universal через lipo. Оговорка про размер и самодостаточность: у любой WebView-оболочки (и Wails, и Tauri одинаково) движок рендеринга — системная зависимость, а не часть бинаря. На Windows и macOS это безболезненно (WebView2 предустановлен в Win11, WKWebView — часть ОС), но на Linux Wails v3 по умолчанию требует GTK4 + WebKitGTK 6.0, а GTK3 + WebKit2GTK 4.1 остаётся лишь через -tags gtk3 и удаляется в v3.1. Заявленная базовая линия — Ubuntu 24.04. На старых LTS (Debian 12, где пакет 6.0 доступен в основном через sid/trixie) это означает либо сборку с -tags gtk3 на время серии v3.0.x, либо отказ от поддержки. Для аудитории в 6-15 друзей риск управляемый, но целевые дистрибутивы стоит зафиксировать в README.

### [info] Остальной фронтенд-стек проверен и актуален — менять нечего

Сверка с npm на 21.08.2026. react — latest 19.2.8 (canary-ветка 19.3.0, то есть React 20 не существует и React 19 остаётся текущей мажорной линией). zustand — 5.0.15, MIT, v5 актуальна. tailwindcss — 4.3.3, MIT, v4 актуальна. Единственная альтернатива, которую имеет смысл держать в уме, — @tanstack/react-store, но он в версии 0.11.1, то есть до 1.0, и брать его вместо зрелого zustand 5 было бы ровно тем хайпом, которого просили избежать.
